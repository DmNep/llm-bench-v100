# ТЗ: полный прогон Qwen3-235B-A22B-Instruct-2507 на termv100 (все режимы × все окна контекста)

## Контекст

На termv100 (Ubuntu, Tesla V100-SXM2 32 ГБ, сейчас 112 ГБ ОЗУ после физической перестановки планки — проверить `free -h` перед стартом, может уже быть больше, если подъехал 1 ТБ HDD под архив) нужно прогнать новый кандидат — **Qwen3-235B-A22B-Instruct-2507** (235B всего / 22B активных, 128 экспертов, топ-8, обычная MoE без экзотики вроде Mamba, нативный контекст 262 144).

Модель ещё не на сервере. Источник: `huggingface.co/unsloth/Qwen3-235B-A22B-Instruct-2507-GGUF`, квант **IQ4_XS (125 ГБ, один файл или несколько частей — проверить на странице репозитория, раньше у нас gpt-oss/Nemotron были по 1-2 файла с суффиксом `.partNofM`)**.

Движок — тот же `llama-server` из `/opt/llama.cpp` (уже собран с новым MoE-кэшем, коммит после #30112, см. `docs/TOR-moe-cache-fix.md` и `results/RESULTS-moe-cache-fix-2026-10-13.md` — читать перед стартом, там уже есть рабочая методика измерений и известные грабли этого движка).

## Подготовка (сделать первым, до бенчмарков)

1. Проверить свободное место: `df -h ~`. Нужно ~130 ГБ с запасом (файл 125 ГБ + накладные на склейку, если модель разбита на части — см. грабли ниже).
2. **Грабля из этой же сессии, ОБЯЗАТЕЛЬНО учесть**: если модель на HuggingFace разбита на `.partNofM`, НЕ скачивать части рядом с финальным файлом одновременно — при склейке через `cat` может не хватить места даже при наличии свободного места под сам файл (так уже падало с gpt-oss). Правильная последовательность: скачать part1 → `mv` part1 в имя финального файла (без копирования) → `cat part2 >> финальный_файл` → сразу удалить part2. Если частей больше двух — обобщить тот же принцип (переименовать первую часть, остальные дописывать по очереди, каждую удалять сразу после append).
3. Скачивать через `wget -c` с `?download=true` в URL (так заведено на этом сервере), как отдельный `systemd-run`-юнит, чтобы не зависеть от SSH-сессии.
4. Проверить SHA256 после скачивания, если на странице HF он указан.

## Что считается "режимом" (протестировать все)

1. **`--cpu-moe`** — все эксперты на CPU, базовый безопасный режим (минимальный VRAM, ожидаемо самый медленный).
2. **Статичный `--n-cpu-moe N`** — перебрать 2-3 значения N, подбирая по остатку VRAM (как делали для gpt-oss/Nemotron: взять число слоёв/экспертов, прикинуть сколько влезет, подвигать на шаг, смотреть по `nvidia-smi` и логам загрузки, не ловить OOM). У модели 128 экспертов/топ-8 (близко к gpt-oss по форме) — начинать с offset, аналогичного тому, что сработало для gpt-oss.
3. **Адаптивный `--moe-cache-mib N`** — тоже 2-3 размера кэша, аналогично методике из `RESULTS-moe-cache-fix-2026-10-13.md`.
4. **Адаптивный кэш + запись на промах** (если патч из Задачи 3 ТЗ про MoE-кэш всё ещё в рабочей копии на сервере — проверить, не слетел ли после пересборки/перезапуска).

Для каждого режима — найти практический потолок (без OOM, с разумным запасом VRAM, как в прошлых прогонах — не разгонять до 99% занятости без необходимости, это уже один раз давало нестабильность).

## Что считается "окном" (протестировать на каждом рабочем режиме)

Контекст у этой модели — обычное внимание (GQA, не Mamba), поэтому KV-кэш растёт с контекстом нормально, в отличие от Nemotron — рассчитывать память под KV отдельно для каждого окна, не считать, что это "бесплатно".

Ряд окон (аналогично тому, что гоняли для gpt-oss/Nemotron):
- короткий (базовая проверка, ~200 токенов промпт)
- средний (~6000 токенов)
- 32768 (минимальный практический для агентной работы)
- 131072 (половина нативного)
- 262144 (полный нативный максимум)

Если на каком-то режиме/окне модель не влезает в VRAM+RAM даже на `--cpu-moe` — зафиксировать это как факт ("не влезает"), не пытаться искусственно впихнуть ценой урезания до неюзабельного состояния.

## Протокол измерения (тот же, что уже использовался всю эту сессию)

- Промпт — повтор нейтральной фразы (как в прошлых тестах), `temperature 0`, замер `prompt_per_second` и `predicted_per_second` из ответа `/completion` или `/v1/chat/completions`.
- Логировать: `nvidia-smi` (VRAM) до и после прогрева, время загрузки модели, любые падения/OOM — не скрывать, фиксировать как результат, а не как "не считово".
- Все сырые логи — в `/opt/llm-results/qwen3-235b-bench/` (по аналогии с `/opt/llm-results/moe-cache-fix/`).
- Итоговый отчёт — `results/RESULTS-qwen3-235b-2026-MM-DD.md` (дата по факту прогона), markdown-таблицы, без воды, в том же стиле, что `RESULTS-moe-cache-fix-2026-10-13.md` (там хороший пример: конкретные числа, честные оговорки, что не вышло — не приукрашивать).

## Критерии приёмки (что проверю при ревью)

1. Все комбинации режим×окно либо измерены, либо явно помечены "не влезает" с объяснением почему (VRAM/RAM не хватило, на каком шаге).
2. Числа воспроизводимы — я переприбегу к серверу и прогоню 2-3 произвольные точки из таблицы, они должны совпасть в пределах разумной погрешности (5-10%, как и раньше в этой сессии).
3. Если что-то ломает уже работающие сервисы (gpt-oss/Strata на 8091, Nemotron) — обязательно вернуть их в исходное рабочее состояние после тестов (как делали раньше: туда-обратно между Strata/gpt-oss/Nemotron без потери конфигурации).
4. Отчёт содержит явный вывод: какой режим/окно — практический "рабочий" выбор для этой модели на этом железе (аналог того, как мы выбрали `--n-cpu-moe 68` для Nemotron и `--moe-cache-mib 26000` для gpt-oss).

## Что не делать

- Не трогать модели/конфиги gpt-oss и Nemotron без необходимости освободить GPU на время теста — если нужно остановить, останавливать штатно (`systemctl stop`), не убивать процессы напрямую.
- Не коммитить и не пушить ничего в публичный репозиторий без отдельного запроса — только сырые результаты и отчёт в рабочую копию, финальное решение что публиковать — за пользователем.
- Не удалять скачанный файл модели после тестов без явного запроса (следующая сессия может его переиспользовать).
