# ТЗ: починка MoE-кэша llama.cpp (`--moe-cache-mib`) для моделей с большим числом экспертов

## Контекст

llama.cpp недавно (PR [#29887](https://github.com/ggml-org/llama.cpp/pull/29887), [#30112](https://github.com/ggml-org/llama.cpp/pull/30112), октябрь 2026) получил нативный адаптивный GPU-кэш для MoE-экспертов, хранящихся в оперативной памяти: `--moe-cache-mib N`. Идея: держать "горячих" экспертов в видеопамяти по LRU, а не статично назначать слои на CPU/GPU как раньше (`--n-cpu-moe`).

На тесте (V100 32 ГБ):
- **gpt-oss-120b** (128 экспертов, топ-4 активных): кэш работает отлично, даёт **+34% к генерации** и экономит VRAM относительно ручной статичной настройки `--n-cpu-moe`.
- **Nemotron-3-Super-120B** (512 экспертов, топ-22 активных, гибрид Mamba-2 + LatentMoE): кэш **катастрофически хуже** ручной настройки — chтение запроса просело **в 16 раз** (с ~115-150 ток/с до ~6.6-7.1 ток/с), генерация тоже ниже (7.9-8.4 против 10.5 ток/с).

Нашли корневую причину в исходнике (`src/llama-moe-cache.cpp`, файл приложен/доступен в репозитории `ggml-org/llama.cpp`, актуальный на коммит после #30112).

## Корневая причина

Кэш работает в двух режимах в зависимости от размера микробатча (см. `impl::get_slot_map`):

```cpp
ggml_tensor * get_slot_map(int32_t il, int64_t n_tokens, int64_t n_expert_used) const {
    ...
    // large batches use most experts of a layer, so they gain little from the cache
    // and would evict the experts used in generation
    if (n_tokens == 0 || n_tokens > max_batch ||
        std::min(n_tokens*n_expert_used, l.slot_map->ne[1]) > groups[l.ig].n_slots) {
        return nullptr;
    }
    return l.slot_map;
}
```

где `max_batch = 32` — захардкожено (`static constexpr int64_t max_batch = 32;`).

Если `get_slot_map` вернул `nullptr` (большой батч), управление уходит в `copy_experts` — он **только читает** то, что уже случайно лежит в кэше с прошлой генерации, и **никогда ничего туда не докладывает** во время большого батча (prefill):

```cpp
int64_t copy_experts(...) {
    ...
    const int32_t * slots = g.lru.slot_map[b.il];
    if (slots == nullptr || slots[e] < 0) {
        return 0; // промах — просто ничего не копируем, эксперт читается с CPU как обычно
    }
    ...
}
```

**Почему это убивает именно Nemotron, а не gpt-oss:**

1. Порог перехода в "большой батч" режим — не только `n_tokens > 32`, но и условие `min(n_tokens*n_expert_used, n_expert) > n_slots`. У Nemotron `n_expert_used=22`, так что уже при микробатче ~20+ токенов `n_tokens*22` легко превышает число слотов кэша (который физически вмещает лишь малую **долю** от 512 экспертов на наш VRAM-бюджет) — активный режим отключается почти сразу.
2. В read-only режиме (prefill) hit rate зависит от того, какая доля экспертов модели вообще помещается в кэш. У gpt-oss (128 экспертов) кэш на наш бюджет покрывает большую их долю → высокий hit rate даже read-only. У Nemotron (512 экспертов) та же VRAM покрывает маленькую долю → почти всегда промах, и движок тратит время на проверку кэша впустую, при этом всё равно читая эксперта с CPU.

Итог: для моделей с **большим общим числом экспертов относительно вместимости кэша** текущая реализация не просто "не помогает", а добавляет чистый оверхед без пользы.

## Задачи

### Задача 1 — Диагностика (низкий риск, делать первой)

Добавить (или включить through existing `LLAMA_LOG_INFO`/отдельный verbose-флаг) метрики hit-rate **раздельно по размеру батча**:
- для микробатчей в "активном" режиме (`n_tokens <= max_batch` и прошли порог по слотам) — уже логируется (`stats_small`/`stats_large` в коде), но стоит явно вывести cutoff, на котором конкретный слой переходит в read-only (с учётом `n_expert_used` и фактического `n_slots`), чтобы по логам сразу было видно: "слой X перешёл в read-only начиная с батча Y токенов".
- для read-only режима (`copy_experts`) — hit rate уже считается (`stats_copy`), но нужно вывести его отдельно по каждому прогону/модели в понятной форме (сейчас видно только в деструкторе при логах уровня INFO).

Прогнать на Nemotron и gpt-oss с разными `--moe-cache-mib`, подтвердить цифрами гипотезу выше (ожидаем: у Nemotron read-only hit rate << у gpt-oss при сравнимой доле VRAM-бюджета).

**Результат**: короткий отчёт с реальными hit-rate/miss-rate цифрами по обеим моделям, разным размерам кэша и контекста.

### Задача 2 — Параметризация `max_batch`

Вынести `max_batch` (сейчас `static constexpr int64_t max_batch = 32`) в CLI-параметр (например `--moe-cache-max-batch N`, по умолчанию 32 для обратной совместимости).

Дополнительно — рассмотреть, не стоит ли сделать порог **динамическим**: не фиксированным числом токенов, а производным от `n_slots / n_expert_used` (чтобы для моделей с маленьким кэшем относительно числа экспертов порог сам подстраивался ниже, а для моделей с большим покрытием — мог быть выше 32).

Прогнать на Nemotron с разными значениями порога (например 8, 16, 32, 48, 64) и посмотреть, есть ли выигрыш от расширения активного (LRU-управляемого) режима на большие батчи, раз у неё и так маленькое покрытие экспертов.

**Результат**: патч с флагом + сравнительная таблица скорости по разным порогам на Nemotron.

### Задача 3 — Write-through прогрев кэша в большом батче (самое ценное)

Сейчас `copy_experts` для большого батча — чисто read-only (см. код выше). Нужно сделать его **write-through**: когда эксперт промахивается в кэше во время обработки большого батча (prefill), после чтения его веса с хоста для вычисления — заодно **положить его в кэш** (как промах в обычном LRU `plan()`), вытесняя наименее используемый, как в активном режиме.

Это даст эффект "прогрева": к концу длинного prefill кэш будет содержать реально релевантный для этого запроса набор экспертов, и переход к генерации (где снова активный LRU-режим) начнётся не с холодного кэша, а с уже тёплого — особенно важно для длинных диалогов/промптов, где новая генерация продолжает ту же тему.

Технически: скорее всего нужно переиспользовать логику `moe_cache_lru::plan()` (или её часть) внутри `copy_experts`, аккуратно — она сейчас рассчитана на вызов из `copy()` с полным списком `ids` микробатча разом, а `copy_experts` вызывается поэкспертно/диапазонами (`e`, `last`). Нужно аккуратно развести потокобезопасность/порядок вызовов (в коде есть прямые указания на это в комментариях: "the next copy synchronizes the backend before it changes the slot map again").

**Риск**: это самая рискованная из трёх задач — трогает эвикшн-логику в горячем пути. Любые изменения здесь **обязательно** тестировать не только на скорость, но и на корректность вывода (сравнение ответа модели до/после патча на одном и том же промпте, не должно отличаться — eviction-логика не должна влиять на арифметику, только на то, что лежит в GPU-памяти).

**Результат**: патч + бенчмарки до/после на Nemotron (prefill и генерация) + подтверждение, что ответы модели идентичны.

## Протокол ревью и тестирования

Всё тестируется на реальном железе (V100 32 ГБ, термv100), не в теории:
- Короткий промпт (~80-200 токенов) и длинный (~3000-5000 и ~125000 токенов) — те же тестовые скрипты, что уже использовались в этой сессии.
- Сравнение с уже известными baseline-цифрами:
  - Nemotron без кэша, `--n-cpu-moe 68`: ~10.5 ток/с генерация, ~115-153 ток/с чтение (в зависимости от длины).
  - Nemotron с текущим (нечиненным) кэшем: ~8 ток/с генерация, ~7 ток/с чтение — это находится "хуже baseline", и есть куда расти.
  - gpt-oss с кэшем (контрольная группа, НЕ должна деградировать от правок): ~17-20 ток/с генерация, ~140-160 ток/с чтение — следить, чтобы изменения ради Nemotron не сломали то, что уже хорошо работает у gpt-oss.
- Каждый патч — отдельная ветка/коммит, ревью перед мерджем в наш локальный чекаут на сервере.
- Я (оркестратор) прогоняю финальные цифры лично на сервере перед принятием любого патча.

## Критерии успеха

Nemotron с кэшем должен как минимум **сравняться** с ручной настройкой `--n-cpu-moe 68` по обеим метрикам (чтение и генерация), в идеале — превзойти её (как это получилось у gpt-oss). Если после всех трёх задач улучшения нет — честно фиксируем вывод "для моделей с >300-400 суммарных экспертов текущая архитектура кэша принципиально не подходит" и возвращаемся к статичной настройке как к единственному рабочему варианту для Nemotron.

## Что не делать

- Не трогать логику для стандартных MoE-моделей (gpt-oss и подобные) без явной необходимости — она уже работает хорошо, любой риск регрессии там неприемлем.
- Не пытаться апстримить изменения в `ggml-org/llama.cpp` в рамках этой задачи — сначала проверяем локально, вопрос PR в апстрим решаем отдельно, если результат окажется satisfying и достаточно общим (не хаком только под Nemotron).
- Не трогать multi-GPU часть кэша (#30112) — у нас одна V100, это вне скоупа.
